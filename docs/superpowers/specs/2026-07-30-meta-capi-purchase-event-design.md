# Meta Conversions API Purchase Event — Design

**Date:** 2026-07-30
**Status:** Approved

## Goal

Krenix's own Meta ads (Click-to-WhatsApp, driving conversations for the
"buy a Krenix subscription" funnel) are currently optimized for the
**Conversations** objective — Meta only knows "did this person start chatting,"
not "did this person become a paying customer." The owner reports 90+
conversations with zero sales, and wants to explore switching the ad
objective to **Sales**. That requires feeding Meta a real purchase signal via
the Conversions API (CAPI), which doesn't exist today for the platform's own
subscription funnel (only per-merchant storefront pixels exist, for stores'
own customers — a completely separate, already-built system).

## Attribution constraint (accepted tradeoff)

Krenix's WhatsApp flow uses plain `wa.me` deep links, not the paid WhatsApp
Business Platform (Cloud API). That means there is no `ctwa_clid` (the
click-to-WhatsApp ad click ID) available anywhere in this codebase's data —
inbound WhatsApp messages arrive at a personal number with no referral
metadata. Precise ad-click-to-purchase attribution is therefore not possible
in this iteration. Instead, Meta will be given the customer's hashed
email/phone (standard CAPI "Advanced Matching"), which lets its systems
probabilistically associate the purchase with whichever of its users share
that contact info — a weaker signal than click-ID matching, but still
sufficient to train "who tends to buy" for Sales-objective optimization. The
owner explicitly accepted this tradeoff rather than pursuing the Cloud API
migration now.

## Scope

Fires only for **subscription** confirmations (new activation or renewal) —
not `credit_purchases` (AI-credit/chatbot-message top-ups). Top-ups are
repeat-customer behavior; they don't represent "cold ad traffic converted,"
which is the signal the owner is trying to give Meta.

Fires for **every** path that confirms a subscription, since all three
represent a real sale:
1. Manual super-admin confirmation (the BaridiMob/CIB proof-upload flow —
   this is the path behind the WhatsApp-negotiated Sur Mesure sales the owner
   is specifically worried about).
2. Automatic SlickPay platform-billing webhook confirmation.
3. Automatic SlickPay platform-billing return-route fallback confirmation.

## Architecture

### New environment variables

- `META_CAPI_ACCESS_TOKEN` — server-only secret, generated by the owner in
  Meta Events Manager → [Pixel] → Settings → Conversions API → Generate
  access token. Never exposed client-side (no `NEXT_PUBLIC_` prefix).
- `META_CAPI_PIXEL_ID` — the pixel ID Purchase events report to. Likely the
  same value as the existing `NEXT_PUBLIC_META_PIXEL_ID` (used today only for
  client-side `PageView` tracking via `MarketingPixel.tsx`), but kept as its
  own var since the ad account's reporting pixel could differ.

### `src/lib/meta-capi.ts` (new)

- `isMetaCapiConfigured(): boolean` — true when both env vars are set.
- `normalizePhoneForMeta(phone: string): string | null` — converts Algerian
  local format (`0X XX XX XX XX`, with or without spaces) to the digits-only,
  country-code-prefixed form Meta's hashing spec requires (`213XXXXXXXXX`).
  Returns `null` for anything that doesn't look like a valid Algerian number,
  so a garbage `user_metadata.phone` value never gets sent.
- `sendPurchaseEvent(input: { email: string; phone?: string | null; valueDzd: number }): Promise<void>`
  — no-ops if not configured. Otherwise POSTs to
  `https://graph.facebook.com/v21.0/{META_CAPI_PIXEL_ID}/events` with:
  ```json
  {
    "data": [{
      "event_name": "Purchase",
      "event_time": <unix seconds now>,
      "action_source": "other",
      "user_data": {
        "em": ["<sha256 of lowercased/trimmed email>"],
        "ph": ["<sha256 of normalized phone>"]   // omitted if phone is null
      },
      "custom_data": { "value": <valueDzd>, "currency": "DZD" }
    }],
    "access_token": "<META_CAPI_ACCESS_TOKEN>"
  }
  ```
  Fire-and-forget: catches and logs all errors (network failure, Meta API
  rejection), never throws. A Meta API hiccup must never block or fail the
  actual payment confirmation it's reporting on — this mirrors the existing
  `notifyOwnerByEmail` helper's fire-and-forget contract in
  `src/app/api/super-admin/payments/[id]/route.ts`.

### Hook points (3 call sites, all after the DB write that flips a subscription to active/confirmed)

1. **`src/app/api/super-admin/payments/[id]/route.ts`** — in the `confirm`
   branch (after `subscriptions.status='active'` and the `stores` update),
   alongside the existing `notifyOwnerByEmail` call. Add one
   `admin.auth.admin.getUserById(store.owner_id)` call to read email +
   `user_metadata.phone` (a second lookup beyond the one already inside
   `notifyOwnerByEmail` — not worth refactoring that helper just to share it),
   and call `sendPurchaseEvent` with `valueDzd: PLAN_AMOUNTS_DZD[plan]`.
2. **`src/app/api/webhooks/slickpay/route.ts`** — right where
   `notifyPlatformPaymentConfirmed` is already called after
   `confirmAndActivate` returns `true`, add a sibling call. Only for
   `recordType === 'subscription'` (top-ups are out of scope per above).
3. **`src/app/api/payments/slickpay/return/route.ts`** — same pattern, same
   `recordType === 'subscription'` guard.

For (2) and (3), the store owner's email/phone are fetched the same way as in
(1) — a single `admin.auth.admin.getUserById(storeId owner)` lookup. The
subscription's `amount_dzd` column already holds the exact price paid (set at
checkout time), so `valueDzd` comes from the record itself rather than
`PLAN_AMOUNTS_DZD` in these two paths (more precise — matches what was
actually charged).

## Error handling & edge cases

- No email on the auth user (shouldn't happen — email is required at
  signup) → skip `em`, still send `ph` if available. If neither is present,
  skip the whole call (no matchable user_data means Meta can't do anything
  useful with the event).
- Invalid/missing phone → `normalizePhoneForMeta` returns `null`, `ph` is
  omitted from `user_data`.
- `META_CAPI_ACCESS_TOKEN`/`META_CAPI_PIXEL_ID` unset → `sendPurchaseEvent`
  no-ops immediately, so this ships safely even before the owner finishes
  generating the token.

## Testing

- `normalizePhoneForMeta`: valid Algerian formats (with/without spaces,
  leading 0) → correct `213...` output; invalid input → `null`.
- `sendPurchaseEvent`: mocked `fetch` — asserts URL includes the configured
  pixel ID, `event_name: 'Purchase'`, hashed (not raw) email/phone in
  `user_data`, `value`/`currency` in `custom_data`; asserts it resolves
  (never throws) even when the mocked fetch rejects or returns non-ok.
- `isMetaCapiConfigured`: true/false based on env presence.

## Out of scope

- Migrating to the WhatsApp Business Platform (Cloud API) for `ctwa_clid`
  click-level attribution — explicitly deferred; the owner accepted
  phone/email matching for this iteration.
- Firing this event for `credit_purchases` (top-ups).
- Any change to the per-merchant storefront Pixel system (`MarketingPixel.tsx`
  equivalents for stores, `pixel-events.ts`) — that's a separate, already-built
  system serving a different purpose (store owners' own ad accounts).
